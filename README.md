# Coop Platform: P04 + P05

Working prototype for **Project 4 (Discovery & Application Tracking)** and
**Project 5 (AI-assisted Matching)**. One app that runs end to end
(screen → API → rules + bounded-AI logic → SQLite), organised as four
**simulated role views**: Student, Employer reviewer, University coordinator
and Faculty reviewer.

> **Sprint 1 (walking skeleton):** Layla (COOP-B001) gets rules-based
> recommendations with reasons, gaps and unknowns, opens a published opportunity
> (OP-028), submits an application and sees **Submitted** / **Not placed** —
> still there after a reload.
>
> **Sprint 2 (response and revision):** Layla saves and refines a **draft** before
> submitting. A simulated **employer reviewer** moves her application through
> *Under review → Shortlisted/Declined* with visible actor, timestamp and next
> action (declines need a reason; a declined application can never receive an
> offer). A bounded, labelled **AI term-matching** feature runs *alongside* the
> unchanged rules baseline. A **coordinator** can inspect a flagged
> recommendation, record a **correction request** for the owning module (P01/P03)
> and apply profile corrections as a **new input version**, then rematch — the
> original recommendation stays traceable.
>
> **Sprint 3 (exceptions, offers and handoffs):** the employer makes Layla an **offer**; she
> accepts it (placement *Awaiting university confirmation*, not a placement yet) or declines.
> Only the **coordinator** confirms it, creating one placement (PL-0001) and one **P07 handoff**
> (mock outbox). She can **withdraw** an active application and see its full history. Her Jira
> **gap** links to a **P06** preparation activity from Team P6/P7, and when a **faculty
> reviewer** marks Jira reviewed, matching **reruns** against the new profile version while the
> old run stays traceable.

Stories: Sprint 1 — P05-01, P05-02, P05-03, P04-01, P04-03.
Sprint 2 — P05-04, P05-05, P04-02, P04-04.
Sprint 3 — P04-05, P04-06, P04-07, P05-06, P05-07.

## Data from P01–P03
The app reads the P01–P03 team's export in `app/data/p01p03/` (4 students at their latest
submitted version, 5 listings incl. a closed one and an unpublished one). Draft profiles are
ignored. `tests/test_p01p03_data.py` checks the test cases they built in. To use our own
synthetic set instead: `DATA_SOURCE=fixtures uv run uvicorn app.main:app`. Replacing the files
with a newer export is enough: records reload on every start (delete `app.db` for a clean demo).

## Run

Requires [uv](https://docs.astral.sh/uv/).

```bash
uv sync
uv run uvicorn app.main:app --reload
```

Open http://127.0.0.1:8000. The API docs are at http://127.0.0.1:8000/docs.
To reset the demo data, stop the server and delete `app.db`.

### The interface
The main page uses the Coop design with live external discovery and the university
application workflow. Explore's source selector switches between public live
feeds and P03's team export. External applications open on the listing source. The header's
workspace selector supports student, employer, coordinator, and faculty testing.
These roles are simulated and have no login. The older interface remains at /classic.
The robot opens Team P6/P7's co-op FAQ assistant from
https://lizhengxi25.github.io/waypoint/#/embed.

## Matching rules (rules-v3)
- Only `published` + `open` listings can be recommended.
- **Mandatory:** the student's availability must cover the opportunity dates. Eligibility is
  `eligible` when dates are covered, `ineligible` for a conflict, or `unknown` when any date is
  missing or empty. Only `eligible` results have `compatible: true`.
- Results rank by eligibility (`eligible`, then `unknown`, then `ineligible`), followed by score
  descending and opportunity ID. The interface shows unknown eligibility as "Eligibility needs checking".
- **Preferences:** a sector in the student's interests adds 3, each required skill held adds 2,
  each desirable skill held adds 1.
- Missing required skills are listed as **gaps**. Self-declared skills are never labelled as reviewed.
- **Evidence (new in rules-v3):** a required skill the student holds only as *self-declared* still
  scores, but is also listed as a gap ("reviewed evidence needed") until a reviewer checks it. This
  matches P01 and P06 ("not yet demonstrated"): Layla's self-declared Jira is a gap on OP-028 until reviewed.

## Bounded AI assistance (ai-termmatch-v1)
- A deterministic, offline skill-term matcher: it finds terms in the listing title/description
  (e.g. "Tableau dashboards") that are equivalent to a skill the student already holds
  (e.g. `SK-VIZ`), using the alias map in `app/fixtures/skill_aliases.json` (P05-owned fallback
  pending Scrum-of-Scrums agreement on the shared vocabulary).
- Each match cites the **term**, the **field** it was found in, the **skill** and the student's
  **evidence status**; the method version is stored alongside the separate rules result.
- It **never** changes eligibility, score, gaps or unknowns, and never invents qualifications —
  it can only map terms to skills already on the profile. Labelled "simulated AI" in the UI;
  the rules baseline stays usable on its own.

## AI recommendation insights (ai-insights-v1)
Stored with each run in `recommendations.ai_insights`, under the same bounds (offline,
deterministic, labelled, never changes the rules result or ranking):
- **AI relevance (0–100%)** — TF-IDF cosine similarity between the profile text (interests,
  skills and their aliases) and the listing text, with the top contributing terms. The UI can
  order cards by it as a *view-only* option; the stored rules ranking is unchanged.
- **Summary** — a plain-language restatement of the rules result (a mandatory conflict is never softened).
- **Next steps** — missing skills ranked by the points the rules would add (and how many other
  open listings require them); self-declared required skills get a "get it reviewed" step.
- **Similar open listings** — Jaccard similarity on skills + sector.
- **Draft with AI** — `POST /api/ai/statement-draft` returns a starter statement for the apply
  dialog. It cites only skills already on the profile and saves or submits nothing.

## Application lifecycle (P04)
`Draft → Submitted → Under review → Shortlisted → Offered → Offer accepted | Offer declined`,
plus `Declined` (employer, from Under review / Shortlisted) and `Withdrawn` (student, from
Submitted / Under review / Shortlisted).
- Drafts keep the entered statement; the statement is required at submission.
- Active statuses (duplicate check): Submitted, Under review, Shortlisted, Offered, Offer accepted.
- Every change stores an event with actor, reason (required for declines) and next action.
- An offer needs a shortlisted application and can never follow a decline.
- Placement status is shown separately: `Not placed → Awaiting university confirmation`
  (student accepted) `→ Confirmed` (coordinator only, P04-06). Confirming creates one placement
  and one P07 handoff; confirming again creates neither. A confirmed placement cannot be withdrawn.

## Skill gaps and rematching (P05-06, P05-07)
- Each gap on a recommendation has **Prepare →**: it passes student, skill, opportunity/version,
  recommendation and profile version to P06 and shows Team P6/P7's activity for that skill
  or, when there is none, a clear next action. Marking the activity done never changes the
  recommendation.
- A student can change availability, and the faculty reviewer can mark a skill reviewed (with an
  evidence ID). Each creates a new profile version and reruns matching; earlier runs keep their
  versions. Same inputs + method versions give the same rules result (the AI is deterministic too).

## Corrections (P05-05)
A student flags a recommendation (reason + affected field). The coordinator sees the input
versions used, records the request for the owning module (P01/P03) and — for profile
corrections (availability, interests) — applies it as a **new profile version** (the fixture is
never overwritten). A rematch then stores a new run; earlier runs stay queryable
(`/api/students/{id}/recommendation-runs`). Listing and skill-evidence corrections stay
*recorded* until the live owning modules exist.

## Real vs simulated vs deferred
- **Real:** the rules engine, bounded term matching, stored recommendations and runs,
  drafts, submission, the duplicate/closed-listing checks, employer decisions with history and
  transition rules, correction requests with version-traceable rematching, SQLite persistence,
  simulated role enforcement at the API level (403 on the wrong role).
- **Simulated:** role switching (no login — labelled in the sidebar), employer/coordinator
  actors, AI assistance (deterministic, labelled). Profiles and listings come from the
  P01–P03 team's file export (24 Nov), not a live P01/P03 interface.
- **Also real (Sprint 3):** offers and responses, withdrawal, placement confirmation with a single
  handoff record, gap handoff records, profile updates as new versions with rematching.
- **Simulated (Sprint 3):** P06 activities (fixture), P07 receipt (mock outbox).
- **Deferred:** authentication, live P01/P03/P06/P07 interfaces, evaluation against the baseline
  (P05-08) and joint handoff verification (P04-08) in Sprint 4, applying P03-owned corrections,
  deployment.

## Live discovery and interviews

Explore now defaults to current technology/research advertisements from the
Canonical’s public Greenhouse board and the Remotive public API. Every external listing links to its source; applications are
completed on the provider's website. Results are cached for six hours. A failed
refresh keeps the last successful feed with a stale label. Check each listing's
location restrictions before applying from the UAE.

Select **University listings** to test the P03 application workflow. Student
profiles and approved listings still use the P01/P03 export because live team
endpoints and credentials have not been supplied. Invented company sample jobs
have been removed. Degree requirements remain unknown unless provided.

Employers can schedule/reschedule an interview after shortlisting and mark it
completed after its scheduled start. Students see the time in their local zone,
format, duration, and meeting location. An offer after a scheduled interview
requires completion. The existing direct shortlist-to-offer route remains
compatible with previous callers.

Business rules and proposed alignment with the teams are documented in
[docs/business-rules.md](docs/business-rules.md). Team approval remains pending.
